# ChatWiki 新人代码库导读

> 面向第一次接触 ChatWiki 仓库的同学，帮助你建立“先看哪里、怎么跑起来、怎么逐步深入”的整体认知。

## 1. 先建立全局认知：这是一个“多服务 + 多端前端”的仓库

从仓库结构看，它不是单体二进制，而是由多个 Go 服务、多个前端项目、以及容器编排共同组成：

- `cmd/*`：多个 Go 可执行程序入口（如 `chatwiki`、`websocket`、`crawler`、`plugin` 等）。
- `internal/app/*`：按服务拆分的业务实现，`cmd` 与这里一一对应。
- `configs/*`：每个服务独立的生产配置模板（`config_pro.ini`）。
- `front-end/*`：后台、PC、H5、Electron、SDK、开放文档等多个前端子项目。
- `docker/docker-compose.yml`：本地/服务器部署时的核心编排文件。
- `build/*`：各服务对应的编译产物入口（容器中直接运行这些二进制）。

**建议你先接受这个事实：ChatWiki 的核心复杂度来自“服务协作”，不是单个目录代码量。**

## 2. 后端主线：以 `chatwiki` 服务为核心，其他服务做能力补充

建议你把 `cmd/chatwiki/main.go` 和 `internal/app/chatwiki/program.go` 当成第一阅读入口，它们清楚回答了“系统启动会做什么”：

1. 初始化（配置、基础组件）。
2. 执行 PostgreSQL 迁移与默认数据初始化（角色、默认用户、默认模型）。
3. 启动 Web 服务。
4. 启动消费者（NSQ topic/channel 的异步任务）。
5. 启动 cron 定时任务。

从 `program.go` 也能看出几个关键运行机制：

- **异步任务总线**：大量业务依赖 NSQ 消费处理（如文档转换、抓取、导出、公众号相关同步）。
- **定时任务体系**：由 cron 调度，负责清理、同步、健康检查、触发器执行等。
- **启动期自动建表/迁移**：迁移脚本直接 embed 到二进制中，启动自动执行。

所以，新人调试后端时，别只盯 HTTP 接口；要同时关注：

- 是否有消息进队列、消费是否成功。
- 定时任务是否触发。
- 各依赖（PostgreSQL、Redis、NSQ、Neo4j）是否就绪。

## 3. 部署与依赖：`docker-compose` 就是系统“运行拓扑图”

`docker/docker-compose.yml` 基本定义了本项目的运行版图，你可以把它当“架构事实来源”：

- 基础依赖：`postgres`、`redis`、`neo4j`。
- 中间件：`go_nsq_service`。
- 核心 Go 服务：`go_core_service`、`websocket`、`code_run`、`gen_thumbnail`、`plugin`、`crawler`。
- 其他配套服务：如文件传输、公众号文章抓取服务等。

建议新人首次排障按这个顺序：

1. 基础依赖容器健康（特别是 Postgres/Neo4j）。
2. 中间件（NSQ）是否工作。
3. 核心 Go 服务是否都启动。
4. 最后再看前端访问与业务联调。

## 4. 前端主线：不是一个前端项目，而是多端并行

`front-end/` 下存在多个独立项目。新人常见误区是“只跑一个就够了”。更实际的做法是：

- 先明确你负责的是哪一端（管理台、PC、移动端、Electron）。
- 进入对应子目录，按各自 README 执行安装、启动、构建命令。
- 统一把“后端 API 地址、鉴权、跨域”作为联调第一检查项。

## 5. 新人必须优先理解的 7 个主题

按优先级排序：

1. **服务边界**：每个 `cmd/*` 服务解决什么问题。
2. **配置体系**：`configs/*/config_pro.ini` 里的关键项与环境变量映射。
3. **数据流**：用户请求 -> 主服务 -> 异步任务 -> 回写/推送。
4. **消息队列**：NSQ topic/channel 的用途、失败重试与堆积定位。
5. **定时任务**：哪些业务依赖 cron，延迟执行是否可接受。
6. **数据库对象**：PostgreSQL + Neo4j 在各场景分别存什么。
7. **多端前端关系**：不同前端如何共享接口、静态资源如何发布。

## 6. 推荐学习路径（2 周版本）

### 第 1~2 天：跑通与观测

- 先按仓库 README 跑起 Docker 部署，拿到可登录系统。
- 记录每个容器职责与端口，建立你自己的“服务清单”。

### 第 3~5 天：读启动链路

- 精读 `cmd/chatwiki/main.go` 与 `internal/app/chatwiki/program.go`。
- 梳理初始化、迁移、消费者、定时任务四条链路。

### 第 6~8 天：读一条完整业务链

- 任选“知识库导入”或“公众号消息处理”做端到端追踪。
- 从 API 入参开始，追到 DB 落库、消息投递、异步消费、结果返回。

### 第 9~10 天：补齐工程化

- 学会本地构建各服务与前端子项目。
- 熟悉日志位置、常见报错、重启策略、配置覆盖方式。

### 第 11~14 天：开始贡献

- 先从“低风险改动”入手：日志补充、文案修复、小型接口增强。
- 每次改动都给出影响面（服务、接口、依赖）和回滚方案。

## 7. 给新人的实操建议（非常重要）

- **先画图再改代码**：把请求流与异步流画出来，效率会高很多。
- **建立本地排障模板**：启动失败、连不上库、消息不消费，分别固定检查步骤。
- **每次只动一个服务边界**：避免同时改 API、队列消费者、前端三处导致难以定位。
- **重视配置漂移**：本地能跑不代表线上能跑，配置项与依赖版本要核对。
- **把“可观测性”当功能做**：关键路径补日志、埋点、错误上下文。
